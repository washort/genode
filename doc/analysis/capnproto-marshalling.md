# Is the Cap'n Proto message format suitable for Genode RPC marshalling?

Follow-up to [component-ipc.md](component-ipc.md). The question: given
Genode's documented reasons for refusing an IDL, is the Cap'n Proto *message
format* (not necessarily its RPC protocol) a fit for some of Genode's
marshalling?

## Sources

- Genode's rationale: `doc/release_notes/11-05.txt` (section "New API for
  type-safe inter-process communication"), `doc/release_notes/16-11.txt`
  ("Improved RPC mechanism"), and `doc/release_notes/25-05.txt` ("The Great
  API hardening", which covers moving away from C++ exceptions).
- Cap'n Proto: the upstream repository `github.com/capnproto/capnproto`,
  commit `e866bdba` (2026-09-30), files `doc/encoding.md`, `doc/rpc.md`,
  `doc/cxx.md`, `doc/otherlang.md`, `doc/roadmap.md`, and the C++ sources
  under `c++/src/{capnp,kj}`.
- Not consulted: genode.org, capnproto.org and genode-labs.com were blocked
  by the network proxy, so this analysis does not draw on the Foundations
  book or the 2007 dynrpc paper.

Line counts below are non-blank, non-comment lines, measured with a simple
filter. Treat them as rough.

## TL;DR

- **As a replacement for Genode's base RPC marshalling: no.** It conflicts
  with three things Genode deliberately relies on: compile-time message
  sizing, a runtime without libc or exceptions, and a minimal trusted
  computing base (TCB). In return, the base RPC layer would gain almost
  nothing: Genode's messages are already flat, word-aligned and small, and
  wire size comes out about the same (see §3).
- **Cap'n Proto RPC (the protocol): no.** It is built for high-latency
  networks: promise pipelining, an async event loop, and per-connection
  capability tables. Genode has synchronous same-machine IPC in which the
  kernel transfers capabilities.
- **As a format for structured payloads carried *inside* Genode mechanisms:
  plausible, with conditions.** Examples are an opaque buffer argument of an
  RPC, a packet in a packet stream, or the content of a ROM or report
  dataspace. The format itself is small and well specified, has an
  out-of-band capability table that maps naturally onto Genode's 4-capability
  message slots, and can be read in place without a parse step. It is a
  defensible choice only if the reader is a **small Genode-native
  implementation** generated by a capnp compiler plugin, not the upstream
  `libcapnp` + `libkj` runtime, and only if shared-memory readers copy
  before validating.

## 1. Genode's objections, checked against Cap'n Proto

The 11.05 release notes list the reasons Genode rejected IDL compilers.
Taking them one at a time:

| # | Genode's objection (11.05) | How Cap'n Proto fares |
|---|---|---|
| 1 | IDLs "suggest a lot power (e.g., the ability to communicate arbitrarily complex data types), which microkernel-targeting IDL compilers fail to deliver because of kernel interface constraints (e.g., hard limits with regard to message sizes)" | **Fails.** `Text`, `Data` and `List(T)` have no bound. A list pointer holds a 29-bit element count (`encoding.md`, "Lists"), and the schema language cannot express a maximum length. So the maximum size of a message cannot be computed at compile time. Genode computes it per RPC function (`Rpc_function_msg_size` in `base/include/base/rpc.h`) and sizes stack buffers from it. Kernel limits are hard: the base-hw UTCB is a page minus its header (`base-hw/src/include/base/internal/native_utcb.h:86`), and `Rpc_entrypoint` buffers are 1 KiB. With Cap'n Proto, size violations could only be caught at run time. |
| 2 | IDLs miss "expressions and functionality important to OS development such as easy-to-use bindings to a systems programming language, fine-tuned resource allocation, or the transfer of special IPC items" | **Mixed, better than classic IDLs.** *IPC items:* capabilities are first-class. A capability pointer is just an index into an out-of-band "capability table", whose storage "is the responsibility of the RPC system; in some cases, the table may not even be part of the message content" (`encoding.md`, "Capabilities"). That maps directly onto `Msgbuf_base::_caps[MAX_CAPS_PER_MSG]`. *Resource allocation:* builders can write into a caller-supplied buffer (`FlatMessageBuilder`, `c++/src/capnp/message.h:427`), and readers work in place (`FlatArrayMessageReader`), so Genode's accounted memory could be used. *Bindings:* the generated C++ is accessor classes (`getFoo()`/`setFoo()`), not native C++ types or arguments. It is still a second type system next to C++. |
| 3 | "some IDL compilers have become extremely complex, i.e., comprising more than 60K lines of code" | **Middling.** `c++/src/capnp/compiler/` is about 22.4k lines, and it also needs `libkj`. It is a host-side tool, though: the compiler parses the schema and then hands off to a separately written code-generator *plugin* (`otherlang.md`, "How to Write Compiler Plugins"). Only generated code and the runtime would run on target. |
| 4 | "the integration of an IDL compiler into the tool chain implies build-system complexity" | **Real but manageable.** Genode already builds host tools and has a `ports` mechanism, but `.capnp` → `.h` generation would be a new build-system rule. Nothing in the tree uses capnp, protobuf or flatbuffers today (`grep` over `repos/`). |
| 5 | Generated stubs "raise the question of whether they must by regarded as part of the trusted computing base and, therefore, become subject to human review" | **Fails with the upstream runtime; manageable with a custom one.** Generated headers are mostly inline accessors. The pointer validation that makes untrusted input safe sits in the runtime (`layout.c++` + `layout.h` ≈ 3.7k lines). The minimal "lite" runtime (core capnp files ≈ 8.0k lines plus the `kj` base ≈ 11.6k lines) is far larger than the whole Genode RPC framework (`rpc*.h`, `ipc*.h` ≈ 1.6k lines *including* comments). Upstream's own warning in `doc/cxx.md`, "Security Tips": *"Cap'n Proto has not yet undergone security review. It most likely has some vulnerabilities. You should not attempt to decode Cap'n Proto messages from sources you don't trust at this time."* Genode servers decode untrusted client input by design. |
| 6 | "there is no need to comprehend two levels of abstraction - one systems programming language should be enough" | **Fails by design.** A schema language with its own types, ordinals (`@0`) and evolution rules is exactly a second abstraction level. |

### An objection that came later: C++ exceptions (25.05)

Genode 25.05 removed C++ exceptions from the base framework. It gave two
reasons: exceptions need a general, thread-safe heap that "contradicts with
Genode's rigid resource-partitioning regime", and the compiler cannot check
statically that every error condition is handled. Errors are now returned
as `Attempt<T,E>` values.

Upstream Cap'n Proto goes the other way. `doc/cxx.md` says: *"It is highly
recommended that you enable exceptions. When compiled with
`-fno-exceptions`, Cap'n Proto categorizes exceptions into 'fatal' and
'recoverable' varieties. Fatal exceptions cause the server to crash, while
recoverable exceptions are handled by logging an error and returning a
'safe' garbage value."*

So with exceptions off, malformed input from a client gives either a crash
or a silently substituted default value. A Genode server should instead
return a typed error to that one client. This is the strongest argument
against reusing the upstream runtime.

The upstream runtime also assumes a POSIX environment. `kj/exception.c++`
pulls in `<pthread.h>`, `<sys/mman.h>`, `<execinfo.h>` and `<cxxabi.h>`, and
`kj/mutex.c++` uses `<linux/futex.h>`. That would push capnp users onto
Genode's libc. Base components are deliberately C-free.

## 2. Properties of the format that do suit Genode

These come from `encoding.md`:

- **Position-independent, in-place readable layout.** All pointers are
  relative word offsets, so a message in a dataspace stays valid whatever
  address each side maps it at. There is no parse step, and fields are read
  lazily.
- **Word-aligned like Genode.** All objects are aligned to 8-byte words, and
  primitives to their own size. Genode's `Msgbuf_base::insert` pads to
  machine words too.
- **Single-segment messages need no framing.** A message is a root pointer
  followed by objects. The segment table is only needed for multi-segment
  messages or byte-stream transport.
- **Capabilities stay out of band.** A capability pointer carries only a
  32-bit index into a table that the transport owns. Genode would carry that
  table in the message's capability slots (at most 4), so the kernel still
  performs the actual delegation.
- **Defences against malicious input are part of the spec.** Readers must
  validate pointers lazily at access time, enforce a *traversal limit*
  against amplification through overlapping pointers and huge lists of
  `Void` elements (C++ default 8 Mi words = 64 MiB, `message.h:54`), and
  enforce a *nesting limit* (default 64, `message.h:75`). Genode would want
  far smaller limits, tied to the size of the buffer.
- **Schema evolution.** New fields can be appended without breaking old
  readers. This is useful for long-lived payload formats (reports,
  persistent data, cross-version components) and irrelevant for base RPC,
  where both sides are compiled against the same header.
- **Many language implementations** (Rust, Go, C, OCaml, …; `otherlang.md`).
  This would matter if Genode hosts components written in several
  languages that need to share structured data.

## 3. Wire-size comparison for typical Genode RPCs

Wire size does not decide the question:

| Call | Genode today | Cap'n Proto (single segment, no framing) |
|---|---|---|
| `add(int a, int b)` | opcode 8 B + 2 × 8 B (each argument rounded up to a machine word) = **24 B** | root pointer 8 B + data section 8 B (two `Int32`s share one word) = 16 B, plus 8 B opcode carried outside = **24 B** |
| `foo(Rpc_in_buffer<N> s)` | opcode + size word + bytes rounded up | opcode + root pointer + struct with one pointer word + list pointer + bytes (+ NUL for `Text`) rounded up, so ~1–2 extra words |

Cap'n Proto packs `Bool`s and small integers more densely. It pays for that
with pointers wherever a value has variable size. For Genode's small,
flat argument lists the difference is negligible.

## 4. Cap'n Proto RPC is a different design

`doc/rpc.md` builds the protocol around **promise pipelining** for
high-latency links ("over a satellite link with 1000ms latency"). It assumes
an asynchronous event loop (`kj-async`), per-connection capability IDs, and
"vats" that form connections among themselves (Level 3). Genode's RPC is
synchronous, same-machine and kernel-mediated: a call costs one IPC round
trip, and capability delegation is done by the kernel or core. Pipelining
saves round trips, but a Genode round trip costs microseconds, not network
latency.

The bigger difference is Genode's discipline that a server never makes a
blocking call to its clients. It replaces callbacks with signals, which
carry no payload, and with shared memory. That model sits poorly with
"calls return promises that the server resolves later". Nothing in
Cap'n Proto RPC replaces Genode's session, quota and routing machinery
(`component-ipc.md` §7).

## 5. Where it could work, and how

### 5.1 Candidate uses

1. **Structured content of shared-memory payloads.** Examples: a
   packet-stream packet body or a report/ROM dataspace that today carries a
   hand-rolled struct or text. Values in place, schema evolution and
   multi-language access are real gains here, and no RPC buffer limit
   applies because the dataspace size is fixed at session setup.
2. **An opaque structured argument of an ordinary Genode RPC**, carried in
   an `Rpc_in_buffer<N>`. `N` keeps the compile-time bound, and the
   capability table maps onto the message's capability slots. This makes
   sense only for interfaces whose arguments are genuinely structured or
   versioned (configuration blobs, extensible requests), not for the bulk
   of base and core interfaces.

### 5.2 Conditions for doing it safely

- **Use a custom reader runtime, not libcapnp/libkj.** The encoding spec is
  about 400 lines of Markdown. A reader with bounds checks, a traversal
  limit and a nesting limit, returning `Attempt<…, Decode_error>`, is a
  small piece of code that can be reviewed. Genode-style accessors can be
  generated by a capnp **compiler plugin**: the `capnp` tool feeds the
  plugin a `CodeGeneratorRequest`, itself a Cap'n Proto message. The plugin
  and the `capnp` compiler stay host-only tools, outside the TCB. This
  answers objections 3, 5 and the exceptions/libc problem.
- **Set the limits from the buffer, not from upstream's defaults.** A
  traversal limit of about 1× the buffer size in words, plus a small
  nesting limit, prevents amplification inside a 1 KiB RPC buffer or a
  fixed packet.
- **Copy before reading if the peer can still write.** The spec requires
  lazy validation at access time and says nothing about concurrent
  modification. In a dataspace that the writer can still change (packet
  stream, a ROM the server rewrites), a value can change between check and
  use. Genode's IPC path avoids this by copying into a private buffer
  (UTCB → `Msgbuf`). Shared-memory consumers should do the same for
  anything they validate, or limit themselves to fixed-size values read
  once. I have not audited whether upstream's `layout.c++` reads any
  pointer twice; that would need checking if anyone uses it on shared
  memory.
- **Treat it as a payload format, not as the interface definition.**
  Genode interfaces stay `GENODE_RPC` declarations in C++. This keeps the
  "one language" property (objection 6) for everything except the payload
  types that opt in.

### 5.3 What it would not solve

Objections 1 and 6 remain. Unbounded fields must be rejected at run time,
and payload types live in a second language. If neither schema evolution
nor cross-language access is needed, a plain C++ POD struct in the buffer
already gives in-place reads with zero dependencies. For most Genode use
cases that remains the better choice.

## 6. Open questions worth testing

1. How small can a conforming Genode-native reader be? Prototype one for a
   subset (structs, lists, Text/Data, capability pointers; no far pointers
   if messages are single-segment) and measure it against the ~750
   non-comment lines of Genode's RPC framework.
2. Does any existing Genode protocol actually need schema evolution or
   multi-language access? Report and ROM formats are the most likely
   candidates. Genode currently uses its own `Node`/`Generator` text format
   there (e.g. `Session_state::generate_session_request`), which is
   human-readable and already handled everywhere.
3. Audit upstream `layout.c++` for double fetches before considering any
   in-place reading of writer-mutable memory.
4. Should a capability index in a Cap'n Proto payload be constrained to the
   ≤4 capability slots of the *enclosing* Genode message? It must be for RPC
   arguments. Packet streams have no capability channel, so capability
   pointers would have to be rejected there.
